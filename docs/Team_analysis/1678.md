	- subsystem
		- bases (similar to 2910: the motor code is written once, in frc/lib/bases, and every subsystem extends one)
			- abstraction
				- layers of abstraction, each one only talks to the layer below it:
					- robot subsystem (e.g. Hood) -> base class (ServoMotorSubsystem -> MotorSubsystem) -> MotorIO (abstract class) -> MotorIOTalonFX / MotorIOTalonFXSim -> TalonFX / physics model (PivotSim, RollerSim ...)
					- robot subsystem: only named setpoints (Hood.STOW, Shooter.FERRY ...) and a constructor, about 20 lines, no logic of its own
					- base: everything a motor subsystem needs, including the commands (setpointCommand, followSetpointCommand)
					- MotorIO: remembers the current Setpoint; applySetpoint(setpoint) is the only public way to move the motor, the setXxxSetpoint methods are protected
					- IO implementations: MotorIOTalonFX calls main.setControl(request); MotorIOTalonFXSim extends it and feeds the simulated TalonFX's voltage into a physics model every 5 ms
				- one more layer than 2910: a shared parent, MotorSubsystem
					- SubsystemBase -> MotorSubsystem -> FlywheelMotorSubsystem / ServoMotorSubsystem -> CoupledServoMotorSubsystem
					- MotorSubsystem does once what 2910 writes in both bases: holds the io, periodic() (reads the sensors, telemetry, live PID tuning), getters, applySetpoint, the commands, enable/disable
					- the subclasses only add the "is it there yet?" checks for their kind of mechanism
				- why it can share so much: the control mode is inside the Setpoint, not in the method name
					- Setpoint = what to do to the MotorIO (applier) + control mode (Mode: IDLE, VOLTAGE, MOTIONMAGIC, VELOCITY, DUTY_CYCLE, POSITIONPID) + the target
					- made with factory methods: Setpoint.withMotionMagicSetpoint(angle), withVelocitySetpoint(rpm), withVoltageSetpoint(volts) ...
					- so one applySetpoint(Setpoint) handles every mode, and the parent doesn't need to know which one it got
				- followers are the IO's job, not a subsystem class: followerIDs go in the subsystem's MotorIOTalonFXConfig, and MotorIOTalonFX makes them follow the main motor
				- example, the hood: Hood.mInstance.setpointCommand(Hood.STOW) -> runOnce(applySetpoint(STOW)) -> ServoMotorSubsystem.applySetpoint -> MotorSubsystem.applySetpoint -> io.applySetpoint(STOW) (then the servo updates its homing flags) -> STOW's applier calls io.setMotionMagicSetpoint(kMinAngle) -> MotorIOTalonFX: main.setControl(motion magic request) -> motor turns the hood
			- types
				- MotorSubsystem: also used on its own, for plain rollers (FeederRollers, HopperRollers, IntakeRollers)
				- flywheel subsystem (FlywheelMotorSubsystem)
					- subsystem that need precise speed control
					- nearVelocity(), nearSetpointVelocity(), a debounced "spun up" check
					- Shooter, TunnelRollers
				- servo subsystem (ServoMotorSubsystem)
					- subsystem that need precise position control
					- nearPosition(), soft limits, setpointCommandWithWait() (set the setpoint, then wait until it gets there)
					- homing built in (ServoHomingConfig): when a setpoint near home is applied, it drives at the homing voltage until it stops moving, then sets that as home
					- Hood, IntakeDeploy, Climber
				- CoupledServoMotorSubsystem: a servo whose position is changed by another mechanism moving (corrects with a coupled position, velocity and gearing), not used on the 2026 robot
				- non-motor bases too: LightsSubsystem (LEDs), CameraSubsystem (Cameras)
				- vs 2910: the types don't have different control modes, any subsystem can take any Setpoint; they only differ in their checks and homing
		- establish subsystem
			- extend bases + config file
				- each subsystem is a singleton: public static final Hood mInstance = new Hood();
				- the constructor passes the base what it needs: super(HoodConstants.getMotorIO(), "Hood", kEpsilonThreshold, HoodConstants.getServoConfig())
			- config file: one XxxConstants.java next to each subsystem
				- TalonFX config (gearing, current limits, PID), MotorIOTalonFXConfig (CAN IDs, followers), sim constants, the setpoint values
				- getMotorIO() picks the IO: Robot.isReal() ? new MotorIOTalonFX(config) : new MotorIOTalonFXSim(config, new PivotSim(...))
				- RobotConstants.isEpsilon / isGamma switch some values for another robot (e.g. the shooter's gearing)
			- no RobotContainer: a subsystem is made the first time any code uses its mInstance
				- Robot.robotInit() calls ControlBoard.mInstance.configureBindings(), which touches the subsystems
			- any code can reach any subsystem through mInstance, nothing is passed through constructors (2910 passes everything in from RobotContainer)
		- how to define subsystem
			- base on physical motor/motor groups: one MotorIO per subsystem
				- 11 subsystems: IntakeDeploy, IntakeRollers, HopperRollers, TunnelRollers, FeederRollers, Shooter, Hood, Climber, Drive, LEDs, Cameras (Drive is CTRE swerve, not on the motor bases)
				- the intake is 2 subsystems: IntakeDeploy (the arm, servo) and IntakeRollers
				- motors that always move together (shooter, tunnel rollers, intake rollers) are one subsystem with followers
			- why split this small: a command can only require whole subsystems, so different commands can control the intake arm and its rollers at the same time
			- flat: no layer between the subsystems and the Superstructure (2910 has Shooter over Hood + Flywheel)
			- Superstructure (extends SubsystemBase, no motors): a library of commands that combine subsystems: intake(), shoot(), tuck(), fenderShot() ..., about 1085 lines
			- Shooting (plain class, not a subsystem): the shooting math (targeting, motion-compensated planner, regressions, ShotVerifier); Superstructure asks it for the latest setpoints
		- how subsystem drive hardwares (the logic)
			- no state machine: no WantedState / SystemState enums anywhere (Superstructure's State enum IDLE / OUTTAKE / SHOOT is only a flag)
			- a command applies a setpoint -> MotorIO remembers it and applies it once -> the TalonFX runs its own closed loop (motion magic, velocity PID) and holds it until a new setpoint comes
				- so a fixed setpoint needs no loop: setpointCommand is a runOnce and ends right away
			- a loop that updates the setpoint, only when the target keeps changing: followSetpointCommand(supplier) re-applies supplier.get() every loop
				- e.g. while shooting, the shooter speed and hood angle follow Shooting's latest numbers
			- periodic() doesn't move motors: it reads the sensors (io.updateInputs), sends telemetry, and applies PID tuned from the dashboard; only servo homing sets a voltage by itself
			- the coordination is the order of the commands: sequence(...), parallel(...), waitUntil(() -> spunUp()), either(a, b, condition)
				- e.g. intake(): deploy the arm + spin the rollers -> waitUntil(prefill ready) -> prefillBallTunnel()
	- How command is run
		- when testing (bringupControls, jogControls, shotTuningControls, commented out in configureBindings)
			- trigger -> change setpoint -> subsystem respond
			- e.g. driver.leftTrigger().onTrue(Shooter.mInstance.setpointCommand(Shooter.FERRY))
			- jogControls: ControllerUtil.bindJog() steps a subsystem's setpoint up or down with buttons, between a min and a max
		- during Comp (driverControls)
			- trigger -> superstructure function -> change setpoint -> subsystem respond
			- the superstructure function returns one command built from the subsystems' commands, and the scheduler runs it
			- e.g. right trigger: onTrue(parallel(Superstructure.shoot(), Shooting.followShootOnTheMoveRequest()))
				- shoot(): the shooter and hood follow the latest setpoints -> waitUntil(aligned, spun up, slow enough) -> the hopper, feeder and tunnel rollers feed
			- letting go: onFalse runs another superstructure command (stopShooting() or idle())
			- two buttons wanting the same subsystem: the scheduler interrupts the older command, because every subsystem command requires its subsystem
			- some commands stop with the button: intake().onlyWhile(driver.leftTrigger())
		- autos: one class per auto (LeftSweep ...) extends AutoModeBase, Choreo trajectories chained with prepRoutine(...) and AutoHelpers.fireCommand(...)
		- Robot.java logs every command when it starts, finishes or is interrupted, so the log shows which commands were running
