	- subsystem
		- bases
			- abstraction
				- the subsystems are built on base templates (subsystems/base), so the motor code is written once
				- 5 layers, each one only talks to the layer below it:
					- robot subsystem (the state machine, e.g. HoodSubsystem) -> base class (ServoMotorSubsystem) -> MotorIO (interface) -> MotorIOTalonFX / SimMotorIOTalonFX -> TalonFX / DCMotorSim
					- robot subsystem: decides what to do, never touches a motor, calls a method it gets from its base
					- base: holds the motor code for each kind of mechanism, logs the request, then passes it on to io
					- MotorIO: an interface, one method per control mode (setOpenLoopDutyCycle, setVoltageOutput, setMotionMagicSetpoint ...) + updateInputs() to read the sensors back up, no motor code
					- IO implementations: MotorIOTalonFX calls talon.setControl(...); SimMotorIOTalonFX extends it and sends most requests to DCMotorSim (a physics model) instead
				- the bases never touch the TalonFX directly, they go through MotorIO, so the same subsystem code runs on the robot and in simulation
				- roller and servo are siblings: both extend SubsystemBase and hold their own io, no shared parent
					- so the setters they both need (duty cycle, voltage, neutral mode, motion magic config) are written twice, once in each file
				- the control mode is the method name (setMechanismVelocityPerSecondSetpoint vs setMotionMagicSetpoint), so each base offers different methods
				- example, the hood: setMotionMagicSetpoint(desiredHoodAngle) -> ServoMotorSubsystem logs it, io.setMotionMagicSetpoint(mechanismPosition, slot) -> MotorIOTalonFX: talon.setControl(motionMagicPositionControl...) -> motor turns the hood
			- types
				- roller (RollerMotorSubsystem): spins, no min/max position
					- velocity
					- duty cycle
					- voltage
				- servo (ServoMotorSubsystem): moves to a position between a min and a max
					- position control
					- motion magic
					- also duty cycle and voltage, same as roller
				- other differences
					- neutral mode: roller defaults to coast, servo to brake
					- soft limits: servo turns them on at its min/max, roller turns them off
					- homing: only servo has home(), which drives slowly into the hard stop until it stops moving, then sets that as its zero
					- different getters: roller gives velocity, servo gives position
				- each base also has a WithFollowers version, for several motors driving one joint (one leader, the rest follow it)
					- RollerWithFollowersSubsystem, ServoWithFollowersSubsystem: the subsystem makes the follower IOs itself and tells them to follow the leader
				- servo also has ServoWithFusedCanCoderSubsystem: a servo that also holds a CANcoder IO
				- each base has a matching config class, and these do share a parent: BaseMotorConfig -> RollerMotorSubsystemConfig / ServoMotorSubsystemConfig
		- establish subsystem
			- RobotContainer builds every subsystem in its constructor, one build...Subsystem() method each
				- picks the IO: RobotBase.isSimulation() ? new SimMotorIOTalonFX(config) : new MotorIOTalonFX(config)
				- passes in the IOs, plus the shared RobotState (pose, speeds, vision) and the ConditionalCallbackManager
				- order matters: swerve first, so the pose is updated before the other subsystems run
				- SuperStructure is built last: new SuperStructure(this), it gets the other subsystems from the container
			- a subsystem with several motors builds its other motors itself
				- IntakeSubsystem gets 3 IOs: super(servoIO), then new RollerMotorSubsystem(rightRollerIO) and new RollerMotorSubsystem(leftRollerIO)
				- ShooterSubsystem gets the hood and flywheel IOs and builds HoodSubsystem and FlywheelSubsystem inside
			- config in one place: RobotConfiguration.getRobotConfiguration(RobotIdentity.get())
				- RobotIdentity picks the robot from the roboRIO serial number (REBLITZ, or SIMULATION in sim)
				- ReBlitz.java holds every motor's config (CAN ID, gearing, PID, limits) as config objects
				- MotorIOTalonFX applies that config to the TalonFX when it's made
			- no singletons: every object gets what it needs through its constructor
		- how to define subsystem
			- simple subsystem -> one file
				- extends the base of its main motor, and keeps the other motors as fields
				- IntakeSubsystem: extends servo (the deploy arm), with two roller fields
				- HopperSubsystem: extends roller, with three more roller fields
			- complex subsystem -> first divide based on the base type (roller/servo) -> combine into real large subsystems on the robot with physical meanings
				- HoodSubsystem (servo) + FlywheelSubsystem (roller with followers) -> ShooterSubsystem
				- ShooterSubsystem extends plain SubsystemBase, it has no motor of its own
				- Hood and Flywheel's setWantedState() is package-private, so only ShooterSubsystem can control them
			- SuperStructure sits above all of them (Intake, Hopper, Shooter, Swerve) and coordinates the whole robot
		- how subsystem drive hardwares (the logic)
			- internal state machine -> same mechanism as the larger one, but this is changed by the changes in the larger subsystems
			- every layer has a WantedState and a SystemState enum (SuperStructure calls its SystemState CurrentState)
			- every loop, periodic(): super.periodic() reads the sensors (io.updateInputs) -> handleStateTransition() picks the system state -> applyStates() runs it
			- applyStates() either sets the wanted state of the layer below, or calls a base setter, which goes down the bases' layers to the motor
			- the layer above sets the wanted state of the layer below: SuperStructure -> Shooter -> Hood / Flywheel
			- the system state doesn't always follow the wanted state
				- Intake and Hood stay HOMING until they're homed, whatever is wanted
				- Hopper: wanted DEFAULT -> PRELOADING if the hopper is full and the feeder is empty, otherwise OFF
	- How command is run
		- Trigger call -> set wanted state -> wanted state to system state -> apply state -> state function calls the subsystem code
			- trigger call: in RobotContainer, e.g. rightBumper().onTrue(Commands.runOnce(() -> superStructure.setWantedStateCommand(SCORE_ON_MOVE))), and onFalse sets DEFAULT_STATE
			- set wanted state: the command only changes a variable and ends right away, it doesn't require any subsystem
			- wanted state to system state: every loop, SuperStructure.periodic() calls handleStateTransitions()
			- apply state: applyStates() runs the function for the current state, e.g. scoringOnTheMove()
			- state function calls the subsystem code: setWantedState() and setters like setShotConditions(rpm, angle)
		- each subsystem's periodic() repeats the same steps one layer down, until a base method (e.g. setMotionMagicSetpoint) sets the motor
		- the few commands that keep running (the swerve's default command, the X-button rotation snap) also only pass values to the swerve every loop, they never set a motor themselves
		- autos work the same way: runOnce(set wanted state) steps, put together with waitUntil(...) to wait for the robot to get there
